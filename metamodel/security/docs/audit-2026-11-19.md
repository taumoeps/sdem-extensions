## 2. Verdict

The design holds: security as a cross-cutting layer S (S1–S5) beside A1–A4, on NIST SP 800-53 / CSF 2.0 / STRIDE, switched on per workspace, checked, traced and drawn from one dataset. **The implementation is a sound first version with real correctness gaps in the computed checks (S07, S08, coverage) and in removal**, and a spec that no longer describes what was built. None of the defects corrupts a design — the extension writes only through `sdem change propose` — but several make the review say a design is better or worse protected than it is, which is what a reviewer relies on it for.

| Severity | Count | Meaning |
|---|---|---|
| High | 5 | the review's answer can be wrong, or a documented procedure fails |
| Medium | 9 | wrong in some designs, fails unclearly, or a promised behaviour is missing |
| Low | 9 | documentation, naming, housekeeping |

## 3. What was checked and holds

- Every attribute the rules use exists in SDEM's metamodel (`metamodel/entity-attributes.json`): `encrypted`, `protocol`, `internet_facing`, `security_scheme` (values match), `zone_kind` (has `dmz`), `access_classification`, `personal_information`.
- The standard's rule syntax is valid for `sdem comply`; S01a, S01b, S02, S03a/b, S04 and S06a evaluate on the example. S05a/b and S06b find nothing only because the example has no `implemented` control and no high-likelihood threat.
- `catalogue.json`: 1,196 controls — id, title, family, enhancement, withdrawn only — from NIST OSCAL SP 800-53 Rev. 5.2.0, with the public-domain notice quoted and a sha256. No proprietary text (ISO 27001, CIS) is shipped.
- Output order is deterministic; the AU-2/AU-12 match accepts `AU-12(1)` and rejects `AU-22`; finding the `sdem` program on Windows works (CI proves it).
- Switching the extension on and checking a second, different design (card-fraud-alerts) works; a missing or unsupported extension is refused, never skipped (MX-11a).
- The publish carries no local folder paths (desnre 0.7.8+); the agent quotes the extension's own results and writes rule ids as code.

## 5. Test gaps

- The whole suite is skipped without SDEM; there are no unit tests of the pure logic (`supported()`, the STRIDE map, coverage, S07/S08/SEC-LAYER, the document's escaping) that run without it. CI runs it with SDEM, so it is covered there — but not on a developer's machine.
- `test_review_runs_the_security_standard` passes on an empty result (`all([])` is true) — it cannot catch AUD-06.
- No test makes a standard rule fire (S01a…S06b); the S03b/S06b test only checks the ids are in the JSON.
- Untested: SEC-LAYER, `personal_data_without_sc28`, `unprotected`, catalogue search, comply failure, missing SDEM, Markdown escaping, removal (AUD-01), exceptions on computed checks (AUD-02).

## 9. Part 2 — the integration code (2026-11-19)

An independent, read-only review of the code outside the package: the publisher `sdem-desnre` (`workspace_bundle`, `extension_results`,
`no_local_paths`, `carry_packs`); the DESNRE site (the Security viewpoint in `archview.js`, the 3D colouring in `index.html`, the Security tab,
Health, Metamodel, Connections, Document Output and figure tables in `workbench.html`, the chat panel in `agent.js`); the site's agent
(`security_review`, the 9.7 template and its figure placement, the guide); and SDEM's core changes for extensions (`profile exclude`, retired
link ids, computed rules, the document titles). It ran the publisher, `exclude` and `exception grant` on a scratch copy of the example; the
site's 50 tests and the agent's tests passed.

**Found fine:** no script injection from record names (text nodes throughout; the exported title is escaped); no crash on a design without
a security layer; the red colour only on the Security plates, A1–A4 unchanged; retired ids honoured (a new link took MAP-088 after the
retired MAP-087); `exclude` with no `mappings.json`; the document title change; nothing half-published without the extension (SDEM refuses
the workspace, MX-11a); no prompt-injection path beyond the tools' existing data wrapper; 9.7's placement matches what the document writer
produces. No leaked path was found in a real 709 KB bundle.
